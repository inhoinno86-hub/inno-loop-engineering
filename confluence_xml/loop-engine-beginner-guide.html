01왜 Loop Engine인가요?

개발 요청은 코드를 쓰는 것만으로 끝나지 않습니다. 무엇을 만들지 정하고, 실제로 만들고, 계획대로 되었는지 확인해야 합니다. Loop Engine은 이 과정을 기억 가능한 상태와 파일로 남깁니다.

일반적인 작업 흐름

대화가 길어질수록 “무엇을 하기로 했는지”, “어떤 테스트를 했는지”가 흐려질 수 있습니다. 중간에 멈추면 다음 사람이 같은 맥락을 다시 찾기도 어렵습니다.

  • 계획과 실제 변경이 분리될 수 있음
  • 테스트 결과가 구두 보고로 끝날 수 있음
  • 실패했을 때 다음 행동이 불명확할 수 있음

Loop Engine의 방식

각 단계는 다음 단계로 넘어가기 전에 필요한 파일과 해시를 확인합니다. 그래서 “완료”는 말이 아니라 확인 가능한 증거가 됩니다.

  • 계획·프롬프트·실행 결과의 연결
  • 독립 검토와 정량 기준
  • 실패하면 구조화된 보정 계획으로 재시도

02한 바퀴는 네 단계입니다

처음에는 네 단계를 모두 수행합니다. 검토에서 보완이 필요하면 plan → run → review 세 단계만 다시 돕니다. init은 프로젝트의 출발점을 정하는 단계라 한 번만 수행합니다.

01 · INIT

요청을 이해하기

의도 문서, 제약 조건, 성공 기준을 정리합니다. 서로 다른 관점의 분석과 판정으로 출발점을 점검합니다.

02 · PLAN

실행 가능한 계획 만들기

작업, 검증 방법, 완료 기준을 ID로 연결합니다. 계획은 다음 단계가 참조하는 기준 문서입니다.

03 · RUN

계획대로 만들기

make-prompts가 단계별 작업 지시를 만들고, exec-prompts가 실행합니다. 결과와 검증 기록을 남깁니다.

04 · REVIEW

증거로 확인하기

계획의 각 기준을 실행 결과와 비교합니다. 통과하면 완료, 부족하면 보정 계획을 만들어 다시 계획합니다.

중요: 재계획은 실패 선언이 아닙니다. 검토에서 찾은 부족한 부분을 다음 실행 계획에 정확히 반영하는 정상적인 루프입니다.

03“완료”를 증명하는 파일들

Loop Engine은 한 문장의 완료 보고만 믿지 않습니다. 아래처럼 서로 연결된 기록을 남겨, 나중에 왜 그런 결론에 도달했는지 추적할 수 있게 합니다.

◎

계획과 검증표

작업 ID, 완료 기준 ID, 테스트 ID가 연결됩니다. 어떤 테스트가 어떤 요구를 확인하는지 알 수 있습니다.

↳

프롬프트 패키지

계획의 특정 버전에 묶인 실행 지시서입니다. 오래된 계획에서 만든 패키지는 새 계획에 사용할 수 없습니다.

▣

실행 보고서와 영수증

실행한 명령, 테스트 결과, 변경 파일, 작업별 결과를 기록합니다.

✓

검토 결과

각 완료 기준에 PASS, FAIL, BLOCKED 또는 증거 부족을 기록하고, 근거를 연결합니다.

왜 해시(hash)를 쓰나요?

해시는 파일 내용의 지문입니다. 계획을 바꾼 뒤 예전 실행 결과로 “통과했다”고 말하는 실수를 막습니다.

계획 v4
execution-plan hash: 8a1…
↓
이 계획으로 만든 프롬프트
prompt-package hash: 42c…
↓
이 프롬프트의 실행 결과
run-report hash: c91…
↓
검토는 위 세 값을 모두 확인

즉, 검토자는 “테스트가 있었다”가 아니라 “현재 계획을 위한 테스트가 통과했다”를 확인합니다.

04자동으로 진행하고, 필요한 때만 멈춥니다

일상적인 계획·실행·검토·재계획은 자동으로 이어집니다. 다만 되돌리기 어렵거나 사람의 판단이 필요한 일은 HIL(Human in the Loop)로 멈춥니다.

AUTOMATIC

계속 진행

일반적인 구현, 테스트, 계획 보정은 사용자 확인 없이 다음 단계로 넘어갑니다.

BLOCKED + ALERT

판단을 요청

외부에 영향을 주거나, 보안·개인정보·예산·핵심 설계 변경이 걸리면 멈추고 근거와 선택지를 알립니다.

FAIL-CLOSED

증거가 부족하면 통과하지 않음

필수 테스트나 검토 증거가 없으면 “아마 괜찮다”로 넘기지 않습니다. 재계획하거나 차단합니다.

최근 추가된 안전장치

  • 알림 outbox: BLOCKED가 생기면 알림 이벤트를 남기고, host adapter가 사용자에게 전달할 수 있습니다.
  • 중복 없는 알림: 같은 알림은 한 번만 전달하고 receipt를 기록합니다. 재개하면 연결된 이전 알림은 자동 해소됩니다.
  • 현실적인 파일 예산: run 시작 전 작업트리 기준점을 저장합니다. 원래 있던 변경과 lifecycle 증적 파일 때문에 예산을 잘못 초과 처리하지 않습니다.
  • 강한 재개 기록: 재개하려면 이전 차단 사유·증거·보정 상태·다음 시도 정책을 함께 남겨야 합니다.

05처음 시작하는 방법

먼저 프로젝트 안에 “무엇을 만들고 싶은지”를 적은 Markdown 파일을 준비합니다. 기술 설계를 완벽하게 쓸 필요는 없습니다. 목표, 제약, 성공 기준을 가능한 한 구체적으로 적으면 됩니다.

1. intent 파일 만들기

# intent.md
사용자가 주문 내역을 조회하는 API를 만든다.

조건:
- 인증된 사용자만 자기 주문을 볼 수 있다.
- 목록과 상세 조회가 필요하다.
- 테스트를 추가한다.

2. lifecycle 시작 요청

$ intent.md를 기준으로
inno-loop 수행 부탁해

엔진은 현재 상태를 확인하고, 새 작업이면 init부터, 중단된 같은 작업이면 안전하게 이어서 진행합니다.

초보자를 위한 팁: “로그인 기능 만들어줘”보다 “이메일과 비밀번호로 로그인하고, 실패 시 오류를 보여주며, 단위 테스트를 추가해줘”처럼 성공 모습을 적으면 검토 기준이 더 분명해집니다.

06자주 묻는 질문

작업 중에 왜 다시 plan으로 돌아가나요?

검토 결과가 현재 완료 기준을 만족하지 못하면, 무엇을 고쳐야 하는지 담은 remediation packet을 만듭니다. 다음 plan은 이 패킷을 입력으로 받아 같은 문제를 놓치지 않도록 합니다.

자동 실행인데 언제 제가 결정해야 하나요?

외부 시스템 변경, 되돌리기 어려운 작업, 보안·개인정보·시크릿, 예산 한도, 핵심 설계 변경, 불확실한 위험처럼 사람이 책임져야 하는 경우입니다. 이때는 BLOCKED 알림에 근거와 가능한 선택지가 함께 남습니다.

실행 중인 상태는 어디에서 보나요?

활성 run의 상태와 증거는 .loop-engine/runs/<run-id>/ 아래에 있습니다. 지속 runner는 terminal outcome 또는 HIL BLOCKED에 도달할 때까지 다음 단계를 이어갑니다.

Superpowers를 항상 실행하나요?

아닙니다. init과 plan의 명시된 통합은 lifecycle 요청 범위에서 사용하지만, 실행 단계의 Superpowers 사용은 별도 opt-in입니다. opt-in이 없으면 일반 Codex 실행과 동일한 증거 계약을 사용합니다.

07기억할 세 문장

  • 계획은 해야 할 일을 정하고, 실행은 그 계획에 묶입니다.
  • 검토는 결과를 믿는 대신 증거를 확인합니다.
  • 자동 진행은 기본이고, 사람 판단은 위험한 순간에만 필요합니다.
  • 재계획은 작업을 다시 시작하는 것이 아니라, 더 정확하게 이어 가는 것입니다.
